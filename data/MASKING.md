# Masked spans in third-party data

The package was checked with an automatic anonymity filter (author, organization, host and local-path terms;
key-shaped strings). A few strings inside THIRD-PARTY content (SWE-bench / SWE-PolyBench / SWE-rebench issue
texts, repository code inside served packs, and model-written patches) match that filter by coincidence, for
example a person-name substring inside a code identifier, an e-mail address in an issue, a user path in a
pasted Windows traceback, or a fake API key in a unit-test fixture. None of them refers to the authors.
Each matching span was replaced by a run of `X` of the same length, so offsets, file sizes in characters and
JSON structure are unchanged. Nothing else in these files was edited. The original (unmasked) sha256 of each
affected file is listed so that it can be matched against hashes recorded in the pre-registrations.
No analysis in the paper reads the masked characters. Hashes are of the uncompressed file; a file listed
here as `x.json` or `x.jsonl` may be shipped as `x.json.gz` / `x.jsonl.gz` (`code/prepare_data.py` restores it).

Total masked spans: 37,709 in 21 files (175 in 16 files outside the read-budget sweep). A span matched by two rules (a name that contains a shorter filtered name) is counted once per rule.

The read-budget sweep's dedup-ON predictions (`data/turncap-sweep/preds_agentic_*_dedupON.jsonl`) hold most of the matches: some of the loop harness's `git diff` patches rewrite whole third-party files such as author lists and translation catalogues, which contain many contributor e-mail addresses. These patches are graded as they were produced; the masking does not change any grading report or loop metric, and `code/analysis/turncap/turncap_recompute.py` does not read patch text.

The original sha256 of `b1b3_packs.json` (`80382193...`) and `b1b3_packs_b2.json` (`7bc29262...`) are the prefixes committed in `preregistrations/LOCAL-B1B3-ADDENDUM-PREREG.md` section 12. Masking replaces the same characters in every copy of a chunk, so the chunk-identity checks in `code/eval/b1b3/b1b3_analyze.py` (nested subset) give the same result on the released files.
